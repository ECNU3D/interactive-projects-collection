## 0. 技术定位与约束

| 约束 | 决定 |
|---|---|
| 纯 Web，无下载 | 首屏可交互 ≤ 5s（有线宽带），总资源 ≤ 40 MB（不含语音） |
| **程序化生成为主** | 几乎不引入外部 3D 模型。建筑、云、地形、特效全部代码生成 |
| 无战斗、无物理 | **不引入物理引擎**。碰撞用简化几何体 + 射线，见 §4.2 |
| 一人可做 | 优先"少量高质量 shader + 大量 instancing"，而不是"大量美术资产" |
| 桌面优先，移动端降级 | 三档画质预设，见 §6.3 |
| 语音全预生成 | 无实时 TTS、无后端推理。**整个项目可以是纯静态站点** |

**最后一条很重要**：因为语音走预生成，本作可以部署为纯静态资源（CDN + 对象存储），没有服务端，没有 API Key 泄露风险，没有并发成本。这个决定极大简化了架构。

## 1. 技术选型

### 1.1 渲染器：WebGPU 优先，WebGL2 兜底

| 项 | 现状（2026-08） | 决定 |
|---|---|---|
| Three.js 版本 | r171 起 WebGPURenderer 转为 production-ready；r184（2026-03）修复了大量每帧对象分配问题 | 锁定 **r184 或更新的稳定版**，开工时 `npm view three version` 确认具体号<br>⚠️ 二手资料把 r171 的发布时间说成 2025-09，与其他来源不符，**待核实**（不影响选型结论） |
| WebGPU 浏览器支持 | Safari 26（2025-09）跟进后，主流浏览器已全面支持 | **WebGPURenderer 为主路径** |
| TSL (Three Shading Language) | 一次编写，编译到 WGSL 与 GLSL | **全部自定义 shader 用 TSL 写**，这是本作能同时支持两条渲染路径的关键 |
| 兜底 | `WebGPURenderer` 在不支持时可回退 WebGL2 backend | 保留回退，但**降级画质档**（关掉体积云 raymarching） |

```js
// 渲染器初始化（异步）
import * as THREE from 'three/webgpu';

const renderer = new THREE.WebGPURenderer({
  antialias: false,           // 用 TAA/FXAA 代替，见 §5.6
  powerPreference: 'high-performance',
  forceWebGL: false,
});
await renderer.init();

const backend = renderer.backend.isWebGPUBackend ? 'webgpu' : 'webgl2';
QualityManager.applyPreset(detectTier(backend));
```

> **待核实**：`renderer.backend.isWebGPUBackend` 的确切属性名随版本变动，开工时以官方 example 为准。

**为什么不保守地只用 WebGL2**：本作的核心卖点是氛围，而氛围的一半来自体积云和体积光。这两样在 WebGL2 上是可以做，但 WebGPU 的 compute shader 让云的 raymarching 可以离屏低分辨率异步推进，帧成本能压到 WebGL2 的 1/3。**这是本作唯一一个值得为之承担新技术风险的地方。**

### 1.2 框架：原生 Three.js，不用 R3F

| 方案 | 评估 |
|---|---|
| **原生 Three.js**（选定） | 本作是一个单场景、单相机、命令式动画密集的应用，React 的声明式模型帮不上忙，反而在每帧更新上要绕路。且 R3F v9 的 WebGPU 支持仍在 `gl` factory prop 阶段，后处理有已知边界情况 |
| React Three Fiber v9 + drei | 适合组件化 UI 重、场景轻的项目。本作相反 |
| R3F v10 | 计划通过 `Canvas` 的 `renderer` prop 默认支持 WebGPU，但**尚在开发中**，不赌 |

**UI 层用什么**：DOM + 一个轻量框架（建议 **Preact** 或纯 TS + Web Components）。对话框、字幕、考据栏全部是 DOM overlay，不进 3D。这样 UI 迭代不影响渲染循环。

## 3. 程序化建筑生成（核心模块）

这是本项目区别于"堆模型"的地方，也是工作量最集中的地方。目标：**用 12 个左右的参数描述一座中式殿宇，一行代码生成一座殿，一个种子生成一百座。**

### 3.1 参数化模型

```ts
interface HallSpec {
  // 平面
  bays: number;            // 面阔间数，奇数。太和殿现存 11，明代奉天殿 9
  depths: number;          // 进深间数。太和殿 5
  bayWidth: number;        // 明间宽（m），次间递减 0.85^n
  columnHeight: number;    // 檐柱高

  // 台基
  podiumTiers: 0|1|2|3;    // 须弥座层数。三大殿共用"三台"
  podiumHeight: number;

  // 屋顶
  roof: 'wudian'|'xieshan'|'zanjian'|'xuanshan'|'yingshan';
  eaves: 1|2|3;            // 檐数。灵霄宝殿原文"三檐四簇"→ 3
  finial?: 'jinhulu'|'baozhu'|null;  // 攒尖宝顶。灵霄宝殿"大金葫芦顶"
  juzhe: number[];         // 举架系数，见 §3.2

  // 装饰等级
  dougongSteps: 3|5|7|9|11;    // 斗拱"踩"数

  tileColor: 'huang'|'huang-lv-jianbian'|'lv'|'lan'|'hei';  // 剪边=黄瓦绿檐口
  doorNails: [number, number]; // 门钉路×排，最高 9×9
}
```

### 3.2 屋顶曲线：举架

中式屋顶的"飞檐"不是直线也不是简单曲线，是**逐步加陡的折线**（清式称"举架"，宋式称"举折"）。这是让屋顶看起来"对"的唯一关键。

清式举架算法：从檐檩往脊檩逐步计算，每一步的举高 = 步架长 × 举架系数，系数序列自檐向脊递增（五举 → 七举 → 八举 → 九举）。

**关键约束：半跨步架数 = (檩数 − 1) / 2。** 系数数组长度必须等于步架数，否则屋面形状是错的。

```ts
// 清式举架系数。数组长度 = 半跨步架数 = (檩数-1)/2
const JUJIA = {
  5: [0.50, 0.70],                    // 五檩：2 步（檐步五举、脊步七举）
  7: [0.50, 0.70, 0.90],              // 七檩：3 步
  9: [0.50, 0.70, 0.80, 0.90],        // 九檩：4 步（大殿标准）
 11: [0.50, 0.65, 0.75, 0.85, 0.95],  // 十一檩：5 步
} as const;

function purlinPoints(spanHalf: number, purlins: 5|7|9|11) {
  const coeff = JUJIA[purlins];
  const steps = (purlins - 1) / 2;
  console.assert(coeff.length === steps, `举架系数个数(${coeff.length})必须等于步架数(${steps})`);

  const stepLen = spanHalf / steps;
  const pts = [new THREE.Vector2(spanHalf, 0)];   // 檐檩
  let x = spanHalf, y = 0;
  for (let i = 0; i < steps; i++) {
    x -= stepLen;
    y += stepLen * coeff[i];          // ← 不做钳位。长度不匹配必须报错，不能静默兜底
    pts.push(new THREE.Vector2(x, y));
  }
  return pts;   // 最后一点即脊檩
}
```

> **明代修正**：明代屋顶举高通常略低于清式，整体系数建议下调 5–8%（即乘 0.93）。这会让屋面更平缓，是"明代感"的一部分。**待核实**具体幅度，建议查《营造法式》与明代实例实测数据。

**屋面网格**：把这条折线作为剖面，沿进深方向拉伸 → 得到前后两坡；庑殿顶再在两山加两坡，四条垂脊由两坡相交得到；歇山顶在庑殿基础上加"山花"与四条戗脊。

#### 翼角起翘（第二难点，README 点名的高风险项）

四个角的檐口要往上翘并向外冲出。这是让屋顶"活"起来的部分，也是最容易做塌的部分。

**两个基本量（清式口诀"冲三翘四"）**

| 量 | 定义 | 取值 |
|---|---|---|
| **冲出 `cornerOut`** | 仔角梁端点相对正身檐口在**水平方向**多伸出的距离 | 约 **3 倍檐椽径**（`3 × d`）。大殿 d ≈ 0.20 m → 冲出 ≈ 0.60 m |
| **翘起 `cornerRise`** | 仔角梁端点相对正身檐口在**竖直方向**抬起的高度 | 约 **4 倍檐椽径**（`4 × d`）→ ≈ 0.80 m。等级越高、体量越大，翘起越强 |

**檐口曲线的构造**

正身段的檐口是水平直线；从"起翘点"开始过渡到角点。起翘点通常取距转角 **3–4 个椽档**处。

```ts
interface EaveCornerSpec {
  rafterDia: number;      // 檐椽径 d
  out: number;            // = 3 * d
  rise: number;           // = 4 * d
  startRatio: number;     // 起翘点距角的距离 / 半跨，典型 0.18–0.25
  power: number;          // 过渡曲线指数，2.0 = 二次，2.6 更"扬"
}

// t: 0 = 起翘点, 1 = 转角
function eaveOffset(t: number, s: EaveCornerSpec) {
  const k = Math.pow(THREE.MathUtils.clamp(t, 0, 1), s.power);
  return { dy: s.rise * k, dOut: s.out * k };
}
```

**建模步骤**

1. 按 §3.2 的举架折线生成**正身屋面**（前后左右四坡，暂不起翘）。
2. 沿檐口线逐点应用 `eaveOffset`，得到起翘后的檐口曲线。曲线在起翘点处的一阶导数应为 0（与正身平滑相接）——`power ≥ 2` 自动满足。
3. **老角梁 + 仔角梁**：从转角柱头沿 45° 方向出两根梁，仔角梁端点落在起翘后的角点上。老角梁在下、仔角梁叠在其上并延伸更远。
4. **翼角椽**：转角区域的椽子不再平行，而是呈扇形排布（"翘飞椽"），根部仍在檩上，端头落在檐口曲线上。用 `InstancedMesh`，逐根算旋转与长度。
5. **屋面蒙皮**：把翼角区域的屋面网格顶点沿檐口曲线做插值抬升，权重同 `eaveOffset` 的 `k`。

**验收**：单独做一个调参页面（lil-gui 暴露上述 5 个参数 + 举架系数），与故宫太和殿、武当金殿的正面/侧面照片叠加对照。**这一关不过，不要往下走。**

> 各地做法差异很大（南方"嫩戗发戗"翘得极高，北方官式含蓄）。本作走**北方官式**，翘起要克制。**待核实**具体尺度，建议查《清工部工程做法则例》的现代整理本。

### 3.3 斗拱

斗拱是**重复构件的极致**，一座大殿有数百攒，每攒又由几十个斗、拱、昂组成。绝不能一个个建 mesh。

```
方案：单攒斗拱 = 1 个合并后的 BufferGeometry（约 300–800 tri）
      整座殿的斗拱 = 1 个 InstancedMesh，instanceCount = 攒数
      整个天宫的斗拱 = 按"斗拱型号"分组，每型号一个 InstancedMesh
```

- 型号维度：踩数（3/5/7/9/11）× 位置类型（柱头科/平身科/角科）= 15 种。**全场只需 15 个 InstancedMesh**。
- **明代特征**：斗拱比宋元显著变小、排列变密、装饰性增强。做"明代感"的关键是**斗拱要密而小**，不要做成唐宋那种硕大疏朗的样子。平身科攒数建议每间 6–8 攒。

#### 单攒斗拱的构件清单

以清式为准。基本模数是"**斗口**"（`D`）——平身科坐斗上安翘昂的槽口宽度，一切尺寸都是它的倍数。九踩大殿取 `D = 0.10 m`。

**自下而上的层级**

| 层 | 构件 | 数量 | 尺寸（斗口 D 的倍数） | 说明 |
|---|---|---|---|---|
| 0 | **坐斗（大斗）** | 1 | 长 3.0D × 宽 3.0D × 高 2.0D | 整攒的基座，落在额枋/平板枋上 |
| 1 | **头翘** | 1 | 宽 1.0D，出跳 3.0D | 垂直于檐面挑出。**每加一踩，多一层出跳构件** |
| 1' | **正心瓜栱** | 1 | 长 6.2D | 平行于檐面 |
| 2 | **十八斗** | 每跳端 1 个 | 长 1.8D × 宽 1.48D × 高 1.0D | 承上一层出跳构件 |
| 2' | **槽升子** | 正心栱两端各 1 | 长 1.72D × 高 1.0D | 带斜面 |
| 3 | **二翘 / 头昂** | 1 | 出跳 3.0D | 昂的下端斜削（"昂嘴"），是斗拱最显著的斜向构件 |
| 3' | **单材瓜栱 / 万栱** | 每跳 1 组 | 瓜栱 6.2D / 万栱 9.2D | 短的在下，长的在上 |
| 4 | **三才升** | 各栱两端与中 | 长 1.3D × 高 1.0D | 最小的斗 |
| 5 | **耍头** | 1 | 出跳 3.0D | 昂之上，端头做"蚂蚱头" |
| 6 | **撑头木** | 1 | — | 耍头之上，不出跳 |
| 7 | **桁椀** | 1 | — | 最上层，承挑檐桁 |
| — | **正心枋 / 拽枋** | 每层 1 | 通长 | 连接相邻各攒，**不属于单攒 geometry**，单独作长条 mesh |

**"每加一踩加什么"的规则**

「踩」= 出跳后横栱的道数。计算式：**踩数 = 2 × 出跳数 + 1**。

| 踩数 | 出跳数 | 出跳构件序列（自下而上） | 用于 |
|---|---|---|---|
| **3** | 1 | 头翘 | 最简，杂役建筑 |
| **5** | 2 | 头翘 + 耍头 | 外围宫殿 |
| **7** | 3 | 头翘 + 头昂 + 耍头 | 次级殿宇 |
| **9** | 4 | 头翘 + 头昂 + 二昂 + 耍头 | 主轴大殿（太和殿即"九踩单翘三昂"，**待核实**） |
| **11** | 5 | 头翘 + 二翘 + 头昂 + 二昂 + 耍头 | 本作不用 |

每增加一跳：出跳构件 +1、十八斗 +2（里外各一）、瓜栱/万栱 +1 组、三才升 +6、拽枋 +1。

**三种位置类型的差异**

| 类型 | 差异 |
|---|---|
| **平身科** | 标准形态。每间均匀排布 6–8 攒 |
| **柱头科** | 坐斗加大（宽约 4D），因为要承梁头；出跳构件逐层加宽 |
| **角科** | 最复杂。三个方向同时出跳（正面、侧面、45° 斜向）。**建议单独手工建一个，不参数化**——全场只有 4 × 建筑数 个角科，且转角本来就被翼角遮住大半 |

**生成实现**

```ts
// Dougong.ts —— 输出单攒的合并 BufferGeometry
function buildDougong(steps: 3|5|7|9, type: 'pingshen'|'zhutou'|'jiao', D = 0.10) {
  const parts: THREE.BufferGeometry[] = [];
  parts.push(box(3.0*D, 2.0*D, 3.0*D));               // 坐斗
  const jumps = (steps - 1) / 2;
  for (let i = 0; i < jumps; i++) {
    parts.push(...tier(i, jumps, D, type));           // 每一跳：出跳构件 + 斗 + 横栱
  }
  parts.push(...topper(D));                           // 撑头木 + 桁椀
  return mergeGeometries(parts);                      // 约 300–800 tri
}
```

**LOD1 及更远不生成实体斗拱**，替换为一条贴了斗拱法线/AO 贴图的檐下带（见 §6.2）。

同理处理：**瓦垄**（一个筒瓦 instance，沿屋面 UV 网格铺）、**栏杆望柱**（一根望柱 + 一块栏板，两个 InstancedMesh）、**螭首**、**脊兽**。

### 3.4 三十三宫七十二殿的布局生成

原著只命名了 10 座（遣云宫、毗沙宫、五明宫、太阳宫、化乐宫；朝会殿、凌虚殿、宝光殿、天王殿、灵官殿），其余 95 座**未命名**——这是程序化生成的合法授权。

```ts
// 布局算法：主轴 + 递归分形院落
// 1. 主轴（南天门→灵霄宝殿）铺 5 个节点，按文档 01 §1.1 的顺序
// 2. 主轴两侧生成 L 层院落，每层用极坐标环形排布 N 座
// 3. 距主轴越远 → 规格越低（脊兽数↓、踩数↓、瓦色 黄→绿）
// 4. 用固定 seed 的 PRNG，保证每次加载布局一致（玩家能记住路）

const RANK_BY_DISTANCE = (d: number): Partial<HallSpec> => ({
  bays:         d < 1 ? 9 : d < 3 ? 7 : 5,
  eaves:        d < 1 ? 2 : 1,
  podiumTiers:  d < 1 ? 3 : d < 3 ? 2 : 1,
  dougongSteps: d < 1 ? 9 : d < 3 ? 7 : 5,
  ridgeBeasts:  d < 1 ? 9 : d < 3 ? 7 : 5,
  tileColor:    d < 2 ? 'huang' : d < 4 ? 'huang-lv-jianbian' : 'lv',
});
```

**关键**：远处的殿宇 **不生成实体几何**，只生成 impostor（见 §6.1）。玩家看到的"宫殿海"90% 是 billboard。

### 3.5 灵霄宝殿的特殊处理

原文写它是「**三檐四簇**」+「**大金葫芦顶**」——这**不是**太和殿式的重檐庑殿，而更接近**多重檐攒尖阁**（天坛祈年殿那一路）。而现实中最高等级的形制又是重檐庑殿。

本作取折中，并在考据栏说明取舍依据：

```ts
const LINGXIAO: HallSpec = {

  bayWidth: 8.0, columnHeight: 14,
  podiumTiers: 3, podiumHeight: 8.13,   // 故宫三台实测

  eaves: 3,                     // 原文"三檐"

  dougongSteps: 9,

```

**实体参考原型**：**武当山金殿**（明永乐十四年，铜铸鎏金，重檐庑殿，山巅云海）。这是《西游记》成书年代真实存在的"人间天宫"——一座用皇家最高规制建造的道教神殿。灵霄宝殿的**材质**照它做（鎏金铜，不是彩画木构），**尺度与仪轨**照太和殿做。

## 4. 玩家与相机

### 4.1 飞行控制器（筋斗云）

**手感优先级**：自由 > 精确。这不是飞行模拟器，是"腾云驾雾"。

```ts
interface FlightState {
  pos: Vector3;
  vel: Vector3;
  yaw: number; pitch: number;   // 朝向
  mode: 'walk' | 'glide' | 'boost';
}

// 关键参数（需反复调）
const P = {
  accel:       28,     // m/s²
  maxSpeed:    45,     // m/s，glide
  boostSpeed:  180,    // m/s，长按 Shift
  damping:     0.995,  // 每帧（60fps 基准）速度衰减。见下方说明
  pitchLimit:  Math.PI * 0.45,
  bankFactor:  0.6,    // 转向时的侧倾，纯视觉
};

// 帧率无关的衰减 —— 直接乘 damping 会让手感随帧率漂移
vel.multiplyScalar(Math.pow(P.damping, dt * 60));
```

**三点手感要求**

1. **松手不立刻停**。`damping = 0.995` 时，1 秒后速度仍有 74%，3 秒后 40%——这才是"驾云"。
   ⚠️ 常见错误是取 0.92：`0.92^60 ≈ 0.007`，一秒内速度掉到 0.7%，那是急停不是滑行。
2. **加速有阶段**。boost 从 45 → 180 m/s 用 1.2s 缓入，同时 FOV 从 65° → 95°，屏幕边缘出现速度线。
3. **贴近建筑时自动减速**。前瞻距离必须**随速度动态计算**，不能写死：

```ts
// 从当前速度减到 safeSpeed 所需的距离 + 余量
const stopDist = (v*v - safeSpeed*safeSpeed) / (2 * P.accel);
const lookAhead = stopDist * 1.5 + 30;   // 180 m/s 时约 900 m
```
   写死 20m 是错的：boost 180 m/s、accel 28 m/s²，从 180 减到 12 需要约 576 m，20m 前瞻少了近 30 倍，玩家会直接穿进殿里。

**移动端**：虚拟摇杆（左移动右视角）+ 双击加速。**不做陀螺仪**。

### 4.2 碰撞（不用物理引擎）

| 需求 | 方案 |
|---|---|
| 不穿墙 | 每座建筑生成时同时产出一个**简化碰撞体**（AABB 或几个 OBB 的并集），存在一个 BVH 里。玩家胶囊体对 BVH 做 sweep test |
| 不掉下云海 | 每层有一个"地面高度场"（可以就是一个函数），低于该高度则施加向上的软约束 |
| 走进殿内 | 殿的碰撞体挖出门洞。生成时把门洞位置记下来即可 |
| NPC 交互检测 | 简单球体距离判断，不进 BVH |

推荐库：`three-mesh-bvh`（如果需要对复杂几何做精确检测）。但优先用**手工简化几何**——程序化生成的好处就是你在生成时就知道碰撞体应该是什么形状，不需要从三角形反推。

### 4.3 相机

- 默认**第三人称**（能看见自己的紫金冠黄金甲，这是扮演感的来源）。
- `C` 键切**第一人称**（看风景用）。
- 第三人称相机用**弹簧阻尼**跟随，不做硬跟随。加速时相机后拉 + FOV 拉伸（可关，见 §4.4）。
- 对话时切**过肩镜头**，NPC 占画面右 1/3，背景虚化（DOF，见 §5.6 后处理管线）。

### 4.4 无障碍与晕动症（必做，不是可选项）

自由飞行 + FOV 拉伸 + 速度线 + 相机晃动，这套组合是典型的晕动诱因。**必须提供开关**，且默认值要保守。

| 设置项 | 默认 | 范围 | 说明 |
|---|---|---|---|
| **FOV 拉伸** | 开 | 开 / 关 | 关闭后 boost 时 FOV 恒定 65° |
| **速度线** | 开 | 开 / 关 / 弱 | |
| **相机晃动** | 50% | 0–100% | 含第三人称弹簧跟随的过冲量 |
| **镜头侧倾（bank）** | 开 | 开 / 关 | |
| **暗角强度** | 30% | 0–100% | 部分人对动态暗角敏感 |
| **移动模糊** | 关 | 开 / 关 | 默认关 |
| **固定参考框** | 关 | 开 / 关 | 开启后屏幕四周叠一层半透明静态边框——这是缓解晕动最有效的手段 |
| **字幕字号** | 中 | 小/中/大/特大 | |
| **字幕对比度** | 标准 | 标准 / 高（纯黑底） | |
| **对话自动推进** | 开 | 开 / 关 | 关闭后需手动点击下一句 |

设置面板必须在**首次进入前**就可访问（放在 loading 页的"入天门"按钮旁），不要求玩家先晕一次再去找。

## 5. 仙气特效管线

这是本作的灵魂。技术细节与美术意图见《03-美术与仙气氛围规范》，此处只写实现。

### 5.1 天空

不用 HDR 环境贴图（太重且不可动）。用 **TSL 程序化天空**：

```
基础：三段渐变（天顶 / 地平 / 云海反光）
叠加：低频 fbm 噪声，产生云絮的色彩不均
叠加：一个"太阳"（不是 DirectionalLight 的可视化，是单独画的辉光盘）
IBL：把这个天空渲染到一个 64×64 的 cubemap，每 2 秒更新一次，作为环境光
```

64×64 的 cubemap 对 IBL 足够（漫反射只需要低频信息），成本可忽略。

### 5.2 云海（最重要的一个效果）

三层叠加，各司其职：

| 层 | 技术 | 作用 | 成本 |
|---|---|---|---|
| **远景云** | 天空 shader 里的 fbm，画在天空盒上 | 地平线的云带 | ~0 |
| **中景云海** | **Raymarched volumetric**，半分辨率 + 时间重投影 | 玩家脚下那片翻涌的云，穿越时有体积感 | 大 |
| **近景云絮** | Billboard 粒子（InstancedMesh + soft particles） | 掠过镜头的云丝，提供速度感 | 小 |

**中景体积云实现要点**

```
1. 渲染到 1/2 或 1/4 分辨率的 RT
2. Raymarch 步数：桌面 48，中档 24，移动端 0（关掉，只留远景+近景）
3. 密度场 = 3D worley 噪声 × 高度衰减窗口 × 一个手绘的"覆盖度"2D 贴图
   —— 覆盖度贴图让美术能控制"哪里有云洞"，是本作能做出"仙山露出云端"的关键
4. 光照：单次散射 + Henyey-Greenstein 相位函数，向太阳方向再 march 6 步取阴影
5. 时间重投影（TAA-style）：每帧只 march 1/4 的像素，用上一帧结果补齐
   —— 这一步把成本降到 1/4，是能在 Web 上跑体积云的前提
6. WebGPU 路径用 compute shader；WebGL2 路径降级为"分层 scrolling noise 平面"
```

**降级方案（WebGL2 / 移动端）**：8–12 层水平半透明平面，每层贴滚动的 fbm 噪声，高度不同、速度不同、透明度不同。远看几乎一样，成本是体积云的 1/20。**建议先做这个版本，把整个游戏跑通，再回头加体积云。**

### 5.3 体积光 / 上帝光

两套并存：

| 类型 | 用途 | 技术 |
|---|---|---|
| **屏幕空间 God Rays** | 太阳、殿门透出的光 | 径向模糊。先渲一张遮挡遮罩（亮源为白、遮挡物为黑），再从光源屏幕位置做 radial blur，加法混合回主画面。成本极低，效果好 |
| **光锥几何体** | 披香殿的香烟光柱、殿内斜射的光 | 手工放置的锥形/楔形半透明 mesh，材质用 TSL 写：沿视线方向的软化 + 噪声扰动 + 深度软化（soft particle，避免与地面硬相交） |

**披香殿是全场体积光的集中展示点**（见文档 01 §1.2 I）。那里同时用光锥 + 高密度 height fog + 香烟粒子，做出完整的丁达尔效应。

### 5.4 雾

`FogExp2` 不够用（它没有高度概念，云海之上和之下应该完全不同）。自写 **height fog**：

```glsl
// TSL 伪代码
fogFactor = exp(-density * distance * exp(-(cameraY - fogBaseY) * falloff))
fogColor  = mix(fogNear, fogFar, saturate(distance / maxDist))
          + sunColor * pow(saturate(dot(viewDir, sunDir)), 8.0) * inscatter
```

三个要点：
1. **高度衰减**：云海层雾浓，往上飞雾迅速变薄。这是"冲出云层"这个体验的全部来源。
2. **太阳内散射**：朝太阳看时雾偏暖偏亮，背对时偏冷。极大提升"空气感"。
3. **雾色不是灰色**。天宫的雾应该是**淡金 / 淡紫**（原文"碧雾蒙蒙""瑞气千条喷紫雾"），见《03》配色表。

### 5.5 粒子

| 效果 | 技术 | 数量级 |
|---|---|---|
| 灵光浮尘（全场常驻） | `InstancedMesh` + 顶点 shader 里做布朗运动，CPU 完全不参与 | 3000–8000 |
| 花瓣 / 瑞草飘落（蟠桃园） | 同上，加旋转 | 500–2000 |
| 香烟（披香殿） | 少量大 billboard + 噪声 UV 扰动 | 30–60 |
| 云絮（飞行时） | Soft billboard，随相机速度生成 | 200–500 |

**统一实现**：一个 `Motes.ts`，用一个 InstancedMesh + 一张属性纹理（位置/相位/尺寸/颜色打包成 RGBA float texture），顶点着色器里读纹理算位置。**CPU 每帧只更新一个 uniform（时间）**。

WebGPU 路径可以用 compute shader 做真正的粒子模拟（碰撞、涡流），但**不是必需**。

### 5.6 后处理管线

顺序固定：

```
主渲染 (HDR, RGBA16F)
  ↓
[体积云合成]      —— 低分辨率 RT 上采样 + 深度感知混合
  ↓
[God Rays]        —— 加法
  ↓
[Bloom]           —— 阈值 1.0 的多级下采样-上采样（Kawase），5 级
  ↓
[DOF]             —— 仅对话镜头启用
  ↓
[Tonemap]         —— AgX 或 ACES。**推荐 AgX**，高光不容易脏，金色更好看
  ↓
[色彩分级 LUT]    —— 32×32×32 3D LUT，给美术一个统一调色的口子
  ↓
[Vignette + 胶片颗粒]
  ↓
[TAA 或 FXAA]     —— 有体积云时必须 TAA（复用重投影的 motion vector）
```

**Bloom 的重要性**：天宫是金色的，金色靠 bloom 才"发光"。但 bloom 过头会糊。建议做**selective bloom**——给发光物体（金顶、灯、法宝、灵光）一个单独的 emissive 通道，只对该通道做 bloom，避免整个屏幕泛白。

### 5.7 材质

统一用 `MeshPhysicalNodeMaterial`（TSL），三套预设：

| 预设 | 用于 | 参数 |
|---|---|---|
| **鎏金铜** | 灵霄宝殿、金顶、法宝 | metalness 1.0, roughness 0.25, 各向异性微弱，clearcoat 0 |
| **琉璃瓦** | 所有屋面 | metalness 0.0, roughness 0.15, clearcoat 1.0, clearcoatRoughness 0.1, 强 specular |
| **汉白玉** | 须弥座、栏杆、丹陛 | metalness 0, roughness 0.6, **transmission 0.05 + thickness**（微弱次表面，让白石在逆光下"透" ） |

**关键**：琉璃瓦的 clearcoat 是让整座宫殿"亮"起来的原因。真实琉璃瓦是在陶胎上施釉，光泽层与本体分离——这正是 clearcoat 建模的东西。不要用高 metalness 假装。

## 6. 性能

### 6.1 预算

| 指标 | 桌面（高） | 桌面（中） | 移动端（低） |
|---|---|---|---|
| 目标帧率 | 60 | 60 | 30 |
| Draw call | ≤ 350 | ≤ 200 | ≤ 90 |
| 三角面（可见） | ≤ 2.5 M | ≤ 1.2 M | ≤ 350 K |
| 纹理显存 | ≤ 320 MB | ≤ 180 MB | ≤ 80 MB |
| 体积云 march 步数 | 48 | 24 | 0（用分层平面） |
| 粒子总数 | 8 K | 3 K | 800 |
| 后处理 pass | 8 | 5 | 3 |

**Draw call 是本作的主要瓶颈**，因为宫殿多。控制手段：

1. **InstancedMesh 一切可重复的东西**（斗拱、瓦、栏杆、柱、脊兽、树）。
2. **BatchedMesh**（Three.js 较新特性）用于"同材质但几何不同"的建筑主体——把 50 座殿的墙体合成一个 draw call，且支持逐实例 frustum culling 和 LOD。**这是本作宫殿海能跑起来的关键 API**。
3. **远景 impostor**：距离 > 400m 的建筑替换为 8 方向 billboard（离线预渲染或运行时首次生成）。宫殿海 90% 是 impostor。

### 6.2 LOD 与剔除

```
LOD0  < 80m   完整：斗拱、瓦垄、脊兽、栏杆逐件
LOD1  80–200m 简化：斗拱合并为一条带纹理的檐下带；瓦垄变法线贴图
LOD2  200–400m 极简：只有体块 + 屋顶剪影 + 一张 baked 贴图
LOD3  > 400m  impostor billboard
```

- **Frustum culling**：Three.js 自带，但对 BatchedMesh 需要显式提供每实例包围盒。
- **Occlusion culling**：不做 GPU occlusion query（Web 上支持差）。改用**层级可见性**——玩家在第三层时，第二层的宫殿海整体降到 LOD2，第一层直接隐藏。分层结构（文档 01 §1.1）本身就是最好的剔除方案。
- **区域流式加载**：`Streaming.ts` 按玩家位置加载/卸载区域模块。每个区域的几何在 Web Worker 里生成，生成完再 transfer 到主线程。**程序化生成必须放 Worker**，否则会卡帧。

### 6.3 画质分档

```ts
type Tier = 'high' | 'mid' | 'low';

function detectTier(backend: 'webgpu'|'webgl2'): Tier {
  // ⚠️ 不要用 UA 判断 iPad —— 现代 iPadOS 的 UA 报的是 Mac
  const mobile = navigator.maxTouchPoints > 1 && !matchMedia('(pointer: fine)').matches;
  if (mobile) return 'low';
  if (backend === 'webgl2') return 'mid';
  // 跑一个 200ms 的微基准，看能不能撑住
  return benchmark() > 0.8 ? 'high' : 'mid';
}
```

档位差异见 §6.1 表。**同时提供手动切换**，并且**运行时自适应**：若连续 3 秒平均帧时间 > 22ms，自动降一档（先降体积云步数，再降粒子，再降后处理）。

### 6.4 加载策略

```
阶段 0 (0–1s)   壳 + loading 画面 + AudioContext 预备
阶段 1 (1–3s)   生成出生区域（齐天大圣府 + 蟠桃园）+ 天空 + 云海 → 可交互
阶段 2 (后台)    生成第二层主轴（南天门→灵霄殿）
阶段 3 (后台)    生成侧翼与其他层
阶段 4 (按需)    语音包按区域下载
```

首屏只需要出生区域。玩家在蟠桃园里转一圈的时间，足够后台把整个天宫生成完。

## 7. 音频架构

内容规格见《04-音频设计文档》，此处只写实现。

### 7.1 用原生 Web Audio，不用 Howler

Howler 的价值在于跨浏览器兼容与 sprite 管理，但它对 **3D 空间音频**的支持是简化版的，且不方便接自定义的混响/滤波。本作的音频有明确的空间需求（捣药声、朝会金钟、殿内混响），直接用 Web Audio 更好控。

```
AudioContext
├── masterGain
    ├── musicBus    → BGM，2 路交叉淡入
    ├── voiceBus    → 对话语音（compressor + 轻微 EQ 提亮）
    ├── sfxBus      → 交互音效
    └── ambientBus  → 环境音
        └── 每个空间音源: AudioBufferSourceNode → PannerNode(HRTF) → ConvolverNode(殿内混响) → ambientBus
```

**Three.js 的 `PositionalAudio` 用不用**：它是 PannerNode 的薄封装，好处是自动跟随 Object3D 的世界变换。**建议用**，但要注意它默认 `distanceModel: 'inverse'`，对大场景需要手动调 `refDistance` / `maxDistance` / `rolloffFactor`。

### 7.2 语音的加载与播放

**问题**：约 1180 条语音，若每条一个文件，就是 1180 次请求。

**方案：按角色打包为 audio sprite。**

```
public/audio/voice/
  taibai-jinxing.webm       # 该角色全部 28 条拼成一个文件（条间留 200ms 静音）
  taibai-jinxing.json       # { "greet_01": [0, 2340], "zhaoan_01": [2540, 5120], ... }
```

- **共 42 个包**：40 个 NPC + **悟空（玩家）** + **旁白/系统**。
  ⚠️ 常见的漏算是只数 40 个 NPC。悟空 300 条 ≈ 20 分钟，是全场最大的一个包。
- 播放：`AudioBufferSourceNode.start(when, offset, duration)`，从 sprite 里切片。
- 格式：**Opus in WebM**（体积约为 mp3 的 60%，全浏览器支持）。降级 mp3。
- 体积估算：单 NPC 28 条 × 平均 4s = 112s，Opus 48kbps 单声道 ≈ 670 KB。全部 ≈ **30 MB**。

**分包与常驻策略**

| 包 | 策略 |
|---|---|
| **悟空包** | **必须常驻，不参与 LRU**。但 20 分钟太大，按对话所在区域拆为 **4–5 片**（天门片、宫城片、内苑片、上层片、通用片），进区域时加载对应片 + 通用片 |
| **旁白/系统包** | 常驻，体积小 |
| **NPC 包** | 按区域预取，走 LRU |
| 单包 > 3 分钟 | 按对话主题再拆 |

**内存必须算清楚**（见《04》§8）：Opus 压缩后 30 MB，但 Web Audio 解码后一律是 **48 kHz float32**。84 分钟全解码 ≈ `84 × 60 × 48000 × 4 B ≈ 970 MB`。**必须做 LRU，移动端上限 4–5 个包。**

### 7.3 自动播放策略

浏览器会阻止未经用户手势的音频播放。处理：

1. loading 页放一个"入天门"的**开始按钮**——这既是必要的用户手势，也是很好的仪式感。
2. 按钮点击时 `await audioContext.resume()`，并播放一段 1 帧的静音 buffer 来彻底解锁 iOS。
3. `visibilitychange` 时 suspend/resume，避免后台耗电。

### 7.4 BGM 分层

不做单曲循环。做 **3 层 stem 的动态混音**：

```
layer_base    垫底的持续音（笙 / 磬 / 弦乐长音）—— 永远在放
layer_melody  旋律层（笛 / 埙 / 琵琶）—— 在开阔区域淡入
layer_grand   宏大层（钟鼓 / 齐奏）—— 靠近灵霄宝殿、朝会事件时淡入
```

三层用同一 BPM 和调性生成（MiniMax 音乐 API 的 prompt 见《04》§4），运行时用 gain 交叉淡入。这样整个天宫只用一首曲子的三个版本，却能做出"随空间变化的配乐"。

## 8. 对话系统

### 8.1 数据格式

内容写在 YAML 里（人可读、可 diff、可交给非程序员维护）：

```yaml
# content/dialogue/taibai-jinxing.yaml
id: taibai_jinxing
name: 太白金星
model: speech-2.8-hd

# 角色级默认参数。参数以《04》§3 为准，本文件是它的机器可读副本
voice_setting:
  voice_id: "Chinese (Mandarin)_Humorous_Elder"
  speed: 1.05
  pitch: 1
  emotion: happy

greet:
  - id: greet_01
    text: "大圣，别来无恙？"
  - id: greet_02
    text: "老汉在此候你多时了。"

topics:
  - id: zhaoan
    label: "当年招安的事"
    source: "第3回、第4回"      # 考据栏引用
    lines:
      - id: zhaoan_01
        speaker: npc
        text: "上圣，三界中凡有九窍者，皆可修仙。"
        quote: true
      - id: zhaoan_02
        speaker: pc
        text: "老星，你这话说得漂亮。"
        voice_setting: { emotion: happy, speed: 1.15 }   # ← 行级 override
      - id: zhaoan_03
        speaker: npc
        text: "一则不动众劳师，<#0.3#>二则收仙有道也。"
        quote: true
    next:
      - { label: "那我这官算什么？", goto: guanzhi }
      - { label: "罢了。", goto: __end }

  - id: guanzhi
    label: "有官无禄是怎么回事"
    source: "第4回"
    lines:
      - id: guanzhi_01
        speaker: pc
        text: "俸禄呢？"
        voice_setting: { emotion: angry, speed: 1.25 }
      - id: guanzhi_02
        speaker: npc
        text: "(chuckle)大圣息怒，且养在天壤之间，何必计较这个。"
    next:
      - { label: "罢了。", goto: __end }

fallback:
  - id: fb_01
    text: "大圣说笑了。"
```

**Schema 约定**

| 字段 | 说明 |
|---|---|
| `voice_setting`（角色级） | 该角色所有台词的默认 TTS 参数 |
| `voice_setting`（行级） | **可覆盖角色级的任意字段**。这是《04》§6.3（悟空逐句切情绪）、§1.4（老君缠磨时提速）落地的必要条件 |
| `model`（可选，可在行级覆盖） | 默认 `speech-2.8-hd`。**需要 `emotion: fluent` 或 `whisper` 的条目必须在此覆盖为 `speech-2.6-hd`**（见《04》§1.3） |
| `quote: true` | 原文直引。UI 加考据角标，点开显示出处。**工具链会校验它在 `quotes-verified.json` 白名单里** |
| `speaker: pc` | 玩家台词，同样预生成语音 |
| `text` 中的 `<#x#>` | 停顿标记，x 为秒数。见《04》§1.4 |
| `text` 中的 `(chuckle)` 等 | 语气词标签，仅 `speech-2.8-*` 支持。见《04》§1.5 |
| `goto: __end` | `__end` 是保留字，表示结束对话。其余值必须是同文件内某个 `topics[].id` |

每一条的 `id` 就是语音 sprite 的 key。**内容与语音靠 id 绑定，工具链自动校验**（见 §9）。

### 8.2 运行时

```
玩家进入 NPC 交互半径 (3.5m)
  → 显示"对话"提示
  → 按 E / 点击
  → 相机切过肩镜头 + DOF
  → DialogueEngine 加载该 NPC 的 yaml（构建时已编译为 JSON）
  → 播 greet（随机一条）
  → 显示 topic 列表
  → 逐行播放：VoiceBank.play(id) + Subtitle.show(text) + NPC 简单口型/头部动画
  → 结束 → 相机复位
```

**NPC 动画**：不做骨骼动画（没有模型来源）。做法是：
- NPC 用**程序化生成的简化人形**（袍服 = 参数化的圆锥+褶皱噪声，这与建筑生成同一套思路）
- 说话时：头部微幅点动 + 袖袍的顶点动画 + 一圈微弱的发光呼吸
- **这是刻意的风格选择**——把 NPC 做成"仙气朦胧的轮廓"，既省掉角色美术，又符合"仙"的表达

### 8.3 考据栏

一个可折叠的侧栏，显示当前场景/角色/台词的原著出处。**这是本作从"技术演示"变成"文化产品"的那一层。**

- 数据源：`content/annotations.json` + yaml 里的 `source` 字段。
- 内容规格见《01》§5：凡自拟设定必须标注"本作设定"，凡异文必须列出。

## 9. 工具链

### 9.1 语音生成 (`tools/gen-voice.ts`)

```
读 content/dialogue/*.yaml
  → 展开所有台词条目，合并角色级 + 行级 voice_setting
  → 注入 content/pronunciation.json 的全局发音词典
  → 与 .cache/voice-manifest.json 比对哈希，只生成变更项（增量）
  → 并发调 MiniMax /v1/t2a_v2 (output_format: 'url', format: 'flac', sample_rate 44100)
  → 立即下载（url 有效期仅 24h），写入 build/voice-raw/{npc}/{id}.flac
  → 保存 subtitle_file（句级时间戳）
  → 更新 manifest
```

要点：
- **生成端要无损**。MiniMax 支持 `format: flac`，直接要 flac + 44100，后面只做一次有损编码（转 Opus）。若走 mp3 32kHz 再转 Opus 48kHz，是有损转有损，白白掉一层质量。
- **必须做增量**。约 1180 条全量重跑既费钱又费时。缓存键 = **整个请求体规范化后的 sha256**（含 `pronunciation_dict`、`language_boost`、`audio_setting`、`voice_modify`、`model`）。只哈希 text + voice_id 会导致改了发音词典却不重新生成。
- 并发度控制在 4–8，注意 `1002 触发限流`、`1039 TPM 限流` 的退避重试。
- API Key 从环境变量读，**绝不写进代码或提交到 git**（当前 `配音配乐/mini_max_api` 里有明文密钥，必须加入 `.gitignore` 并考虑轮换）。
- 开启 `subtitle_enable: true` 可拿到句级时间戳，用于字幕逐句高亮。

### 9.2 音频打包 (`tools/pack-audio.ts`)

```
build/voice-raw/{npc}/*.flac
  → ffmpeg 双遍 loudnorm 归一化到 -16 LUFS（见《04》§7.3）
  → 转 Opus/WebM，48kbps 单声道
  → 按角色拼接，条间插 200ms 静音
  → 输出 public/audio/voice/{npc}.webm + {npc}.json（sprite 索引）
  → 悟空包超长（≈20 min），按对话区域拆为 4–5 片
```

### 9.3 校验

CI 里跑一个 `validate` 脚本：

- 每条 yaml 台词都有对应的语音条目吗？
- 每个语音条目都被至少一条 yaml 引用吗（找孤儿）？
- 所有 `quote: true` 的台词，是否在 `content/quotes-verified.json` 白名单里？（**防止误引原文** —— 这是文档 01 §5 那批讹误的技术兜底）
- 所有 `voice_id` 是否在 MiniMax 系统音色列表里？（**注意放行 `timbre_weights` 分支**——混合音色时 `voice_id` 合法地为空字符串）
- 所有 `emotion: fluent | whisper` 的条目，`model` 是否被覆盖为 `speech-2.6-hd`？
- 所有 `goto` 目标是否存在（或为 `__end`）？
- 所有 `speed ∈ [0.5,2]`、`pitch ∈ [-12,12]`、`vol ∈ (0,10]`？

**`quotes-verified.json` 的格式**

```jsonc
[
  {
    "quote": "三界中凡有九窍者，皆可修仙",
    "chapter": 3,
    "speaker": "太白金星",
    "source": "中文维基文库《西遊記》第003回",
    "verified": "2026-08-08",          // 逐字核对日期
    "status": "confirmed"               // confirmed | disputed | self-authored
  }
]
```

**由谁维护**：从 `docs/research/` 的两份考据笔记生成初始版本，此后每新增一条 `quote: true` 台词，必须先在此文件登记并注明核对日期。**没登记的引文过不了 CI。**
